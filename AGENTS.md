## CI-first testability contract (operator decision 2026-11-11)

- **Everything in `klarkc/os` must be testable by GitHub Actions CI.** Every new feature, NixOS/user module, desktop/application configuration, Windows PowerShell thin-client behavior, script, service, and platform integration must have an automated, repeatable CI verification strategy and corresponding test coverage. A manual procedure or successful user session is useful acceptance evidence, **not** the sole test plan. Do not call a change finished if the relevant CI gate is absent, skipped, failing or unverified.
- **Split tests by purity, not by importance.** Put deterministic, hermetic evaluation, package builds, module assertions, pure unit tests and isolated QEMU/NixOS tests inside `nix flake check` whenever feasible. **GitHub Actions CI is responsible for the tests that `flake check` cannot perform because of Nix purity/sandbox constraints** (for example, network-dependent integration, OS-specific Windows/PowerShell tests, orchestration across processes, or non-pure external tooling). Keep them in versioned `.github/workflows/` jobs with pinned/controlled dependencies and explicit pass/fail criteria; never omit testing merely because it cannot run in a pure derivation.
- **Representative environments and safe boundaries.** Use GitHub-hosted Windows runners for PowerShell client tests with mocked `gcloud.cmd`, NAT/VM states, tunnel and `mstsc.exe`; use Linux/QEMU for NixOS, XRDP, desktop and lifecycle logic. Model external providers using disposable test resources, fixtures, contract tests and mocks before requesting any real provider E2E. Tests must be reproducible and **must not mutate the paid GCE VM, personal credentials, cloud billing, vaults, real devices or production state by default**. Any provider-backed test requiring credentials, real costs or privileged changes needs separately approved opt-in gates and scoped short-lived identity; never log or persist secrets.
- **No untestable exceptions.** If a behavior cannot be covered within a pure Nix check, design a GitHub Actions job to cover it; if it cannot be automated safely yet, mark the CI gap and change as **not release-ready** and define a safe test seam/mock/harness. Device-specific physical acceptance (actual Dell boot, authenticated user vault interaction, real audio hardware and future ARM GPU operation) remains a separate reported E2E gate **in addition to** CI, never a replacement for testing the underlying logic in CI.
- **Avoid duplicated tests and configurations.** Organize shared application/host logic once, extend it in role-specific modules, run common checks once, and add environment-specific CI jobs only for the behavior that differs. Record test ownership and keep actionable failure diagnostics without leaking secrets.

## Unified integration and end-to-end test scripts (operator decision 2026-11-11)

- **No Makefiles.** Do not introduce, depend on or migrate testing to `Makefile`, `make test` or equivalent make targets. Retire any legacy Makefile-based test orchestration when encountered. Keep versioned, executable scripts in the appropriate `tests/` or `workstations/tests/` directory as the **single entrypoints** for each integration/E2E suite, with documented parameters, expected environment and exit status. Helper scripts can be shared, but there must not be separate manual and CI implementations of the same test.
- **CI invokes the identical scripts that developers run manually.** GitHub Actions must call those checked-in scripts rather than duplicating test logic as inline workflow YAML. A developer must be able to reproduce the same integration/E2E result outside CI by invoking the same entrypoint and documented arguments. Keep platform differences in explicit adapters or well-defined parameters, not forked test logic; validate success and failure through nonzero exit codes and useful diagnostics.
- **`nix develop` is the reproducible dependency contract.** Declare all dependencies of Linux/Nix-compatible integration/E2E scripts (interpreters, test runners, CLI tools and helper binaries) in the corresponding version-controlled, lockfile-pinned Nix development shell. Test entrypoints and CI should operate inside that same `nix develop` environment; do not assume global packages, AUR, imperative profile installs or undocumented PATH state. Keep build/test dependencies scoped to the dev shell rather than duplicating them in production profiles.
- **Other operating systems are the exception, not an implicit dependency.** When a script needs Windows or another non-NixOS environment, use the appropriate native runner and dependency setup. At startup, before making changes, validate the OS, required commands, versions, authentication/configuration preconditions and necessary permissions. If anything is unavailable, **fail fast with a nonzero exit code** and an actionable message describing what must be installed and configured (and where to find the maintained setup instructions). Do not silently skip tests, fake success or fall back to a different platform. Windows scripts must document their prerequisites and be exercised on a GitHub Actions Windows runner.
- **Purity boundary:** pure, deterministic checks remain in `nix flake check`; integration/E2E checks that cannot run inside Nix's pure build sandbox live in these reusable scripts and are executed by GitHub Actions with the required runner capabilities. Do not duplicate script bodies in `flake.nix` or CI. Provider-backed operations, paid resources, real user sessions and secrets require explicit opt-in, narrowly scoped credentials and a safe, non-destructive test plan; default CI remains offline/mocked when possible.
- **Keep docs and tests together.** Every integration/E2E change must update its script, `nix develop` dependencies (or OS-specific prerequisite guidance), CI invocation and developer instructions as one reviewed change. A green pure flake check cannot compensate for an absent or failing integration/E2E script; report each gate independently.

## Dual-path OS deployment and remote MCP access (operator direction 2026-11-11)

- **Two independent, complementary application paths for the same declarative NixOS state:** **hot** means a current, authenticated workstation remote-access channel (preferably the owned ChatGPT GCE MCP with an SSH/IAP guest-execution capability) validates a specific reviewed `main` revision, runs the approved preflight/CI-equivalent checks and uses `nixos-rebuild test` or a controlled `nixos-rebuild switch --flake` on the existing running machine. **Cold** means GitHub Actions `deployment.yml` builds/tests and promotes a pinned NixOS closure or immutable image externally, and applies it only through an explicitly approved recovery-safe deployment. Both derive from the **same canonical Nix modules and lockfiles**, never divergent copies. An image build is not a successful guest activation. Hot and cold jobs **may be started concurrently**. GitHub Actions serializes **entire cold deployment workflow runs** using a fixed concurrency group and `queue: max`; the hot MCP remains independent of the GitHub queue. Read-only checks and independent offline `test.yml` builds can run in parallel. A cold activation must first compare its desired **NixOS system toplevel store path** with the running system and the system boot-default profile; if both already match after a verified hot rollout, return **SKIP_UNCHANGED** without reactivating. Compare actual store paths rather than assuming a Git revision or flake input hash means identical activated systems. Also prevent stale queued cold deployments from rolling back a newer verified applied main revision (**SKIP_STALE** with explicit provenance, not a generic success). Report target path, active/boot-default paths, source revision and effective result.
- **Single cold deployment queue, bounded and non-destructive:** `.github/workflows/deployment.yml` uses `concurrency: { group: workstation-deployment, cancel-in-progress: false, queue: max }` at workflow scope. At most one complete cold deployment run executes at a time across refs and triggers; up to 100 others can wait, and requests beyond that bound can be canceled by GitHub. This is **not** a queue for the hot MCP. GitHub orders runs based on when each starts waiting, not necessarily dispatch time. All jobs in `test.yml` remain separately runnable. A queued run is **not** authorization for new cloud costs, production redeploy, or bypass of current authorization.
- **Guest activation arbitration and idempotence:** `SKIP_UNCHANGED` is an explicit checked no-op **only if both** `/run/current-system` and the boot-default `/nix/var/nix/profiles/system` resolve to the expected toplevel store path (for a `switch`), with a verified host identity and completed postflight. A prior `test` activation with an unchanged boot default does **not** qualify. `SKIP_STALE` requires a trusted recorded applied revision and Git ancestry/ordering proof. When both pathways activate on the guest, share one short-lived host-local non-blocking `flock` guarding **final preflight, compare, switch, postflight and generation marker**; a contender reports `SKIP_BUSY` without modification. GitHub Actions concurrency alone cannot prevent the hot MCP from activating concurrently. Do not assume `nixos-rebuild` itself acquires this lock or returns `SKIP_UNCHANGED`.
- **Cold operations outside the guest:** the current image/provisioning-oriented cold workflow does **not** perform an in-place NixOS closure switch, so it cannot claim `SKIP_UNCHANGED` solely from a matching source commit or a green image build. Any future cold action that changes GCE image, boot disk, IAM or instance lifecycle externally must first coordinate with hot guest changes through an appropriate shared provider-side guard and specific approval; a host-local `flock` alone cannot protect out-of-guest actions. Do not provision a new Cloud Storage lock bucket merely to support GitHub's cold-to-cold queue; decide on a cross-plane guard only when the external mutating deployment is designed. On interrupted or UNKNOWN operations, reconcile provider and guest state before resuming; never release ownership purely on timeout or claim successful activation from a CI build.
- **Test and report all outcomes:** reuse checked-in shell scripts to test the queue/activation contract (mock same-target, boot-default mismatch, different-target contention, stale revision, failed switch, and ambiguous provider responses) through `test.yml`. Distinguish `DEPLOYED`, `SKIP_UNCHANGED`, `SKIP_STALE`, `SKIP_BUSY` and `FAILED`; a skipped activation cannot excuse failed mandatory CI tests.
- **Hot path safety:** read-only preflight first; check actual SSH, current generation, access continuity, sufficient disk space and rollback. Do not change the kernel/bootloader, reboot, reset, destroy/recreate the instance, replace the boot disk, alter IAM or close the only RDP/SSH channel as an incidental effect of a hot update. Explicitly authorize material live changes; keep an independently recoverable cold path. A failed rebuild must not claim successful deployment. Any automatic recovery step must be separately authorized and bounded.
- **Cold path safety:** CI owns reproducible evaluation, integration and image/closure tests; production deployment is opt-in, cost reviewed and not triggered by ordinary `main` pushes or Dependabot PRs. Do not overwrite persistent user data or claim rollback of lost in-memory XRDP sessions. Preserve the boot disk or verified snapshot/recovery state and require provider evidence for any actual guest change.
- **Preferred ChatGPT guest access: extend the owned ChatGPT GCE MCP**, not the limited Desktop Commander Remote service. A GCE control-plane API tool cannot execute commands inside a VM merely by broadening its API scope: implement a separate, explicitly authorized guest-execution tool behind the **same MCP** using Google-managed IAP TCP forwarding + SSH/OS Login and narrowly scoped IAM. Do not assume the existing GCE integration already has guest access. Review the actual self-managed MCP backend, authentication and CI before implementation. A separate MCP backend using resources wholly controlled by the operator is fallback only if the existing MCP cannot support the required protocol and identities.
- **No inherited third-party edge infrastructure:** do not migrate historic tunnels, external account resources, external domain credentials or tenancy-specific access settings from the archived user configuration. Any optional gateway for the MCP must run within operator-controlled Google Cloud resources and be separately scoped, authenticated, tested and approved. Never expose raw unauthenticated terminal MCP or SSH/RDP to the public internet. No private hostnames, credentials, project identifiers, accounts or access URLs in this public repository.
- **Guest identity and authorization separation:** GCE lifecycle access, guest SSH access, read-only inspection, write access and privileged NixOS activation are distinct capabilities with separate identities/permissions. Use the least privilege possible, a specific VM and port 22 IAP tunnel, short-lived identity rather than committed keys, and a non-root OS Login account by default. OS Login users may not be the same POSIX account as the XRDP user; never silently modify the other user's HOME. Privileged rebuild is a separately approved, logged escalation or narrow deployment unit; never expose unrestricted root/sudo implicitly through a generic shell tool.
- **Remote-execution MCP contract:** bound every call by host identity, allowed workspace, stable operation ID, command timeout, output/response size and explicit read-only vs mutating intent. Preserve exit status, redact secrets, avoid logging command arguments containing private values, and handle UNKNOWN outcomes by reconciling before retries. Do not assert that shell-command allowlists replace a Linux security sandbox. Design approval boundaries to resist untrusted tool output and prompt injection. Remote shell access on a production VM must never automatically start a stopped/billable instance without operator approval.
- **Testable without production access:** keep all host modules and MCP integration adapters reproducible under the repo's `nix develop`; use common Shell test entrypoints for mocked IAP, OS Login, SSH authentication, command execution, error paths, timeouts, locking, rollback, and privilege boundaries, called verbatim from the single `test.yml` workflow. Any platform-external connector backend must have equivalent contract/integration CI and explicit versioned interfaces. Real authenticated SSH/IAP and `nixos-rebuild` remain separately authorized E2E acceptance gates, not substitutes for mocks. Preserve the file allowlist and public-repository privacy policy.
- **Future host portability:** GCE is currently the remote workstation and may later become a stopped disaster-recovery fallback. The Dell thin client and future ARM workstation reuse the same declarative modules; the MCP transport adapter may differ by host, but tool semantics, identity boundaries, testing, and release provenance must be shared rather than duplicated.

## Carried-forward safeguards from archived dotfiles

These rules replace and adapt the useful parts of archived `klarkc/dotfiles/AGENTS.md`. In case of conflict, the active `klarkc/os` ownership, `main`-only policy and the above phases take precedence; old `$HOME`-is-a-repository, worktree, Arch and `nix profile upgrade klarkc` instructions do **not** apply.

- **Privacy and Git discipline (public repository):** treat tracked content, tests, documentation, commit messages and history as publicly visible. Do not add real customer/organization names, personal identifiers, deployment endpoints, IP addresses, host identities or local user paths in new public examples without explicit publication approval. Prefer synthetic documentation examples and runtime-supplied, ignored configuration. Recheck the exact proposed staged/tree diff for secrets and private metadata before every commit; run existing Gitleaks/pre-commit privacy checks where available; keep scanner reports private and redacted. A negative scan never proves absence of leaks. If suspected exposure is found, stop and report file/line/classification without printing any secret; recommend rotation and obtain approval before any history rewrite. Never bypass hooks with `--no-verify`, `SKIP` or alternate Git paths.
- **Secrets are runtime-only:** no credentials, SSH keys, Enpass vault/profile, browser cookies, OAuth tokens or personal session backups in Git, Nix store, images, cloud metadata, CI output or process arguments. Where the legacy Linux workflow needs `~/.profile_override`, keep this file ignored, readable only by its owner and **values-only** (assignments/exports/comments, no executable logic); derive runtime values in versioned scripts after sourcing it. Other provider-managed private stores or OS keychains may be used only with explicitly reviewed security. Temporary credential material belongs under user-private `$XDG_RUNTIME_DIR` (0700 directory / 0600 files) with bounded lifetime, not to public source. The Windows thin-client may persist nonsecret resource identifiers under the user's private app-data path, but never credentials.
- **Nix reproducibility and no duplicated ownership:** all dependencies fetched by **repo-maintained Nix code** must be declared via appropriate canonical flake inputs and locked revisions/hashes, not live `fetchTarball`, mutable `<nixpkgs>`, `curl`, `git clone`, `npm install` or `pip install` in a Nix build. Prefer Nix-native builders; if an ecosystem resolver must be used, operate offline on already-locked inputs. Upstream derivations are not subject to our repo-maintained-code restriction unless patched or vendored. Do not duplicate the same program's Nix package/profile/service definition across modules; **extend/import** the single owner and use host-specific option overrides only where justified.
- **Coupled updates:** when a source, version, hash or runtime is pinned, add a nearby actionable bump note describing the companion inputs/hashes/wrappers/tests to update. Update coupled parts together. Follow existing Nixpkgs branch input URLs and rely on `flake.lock` for determinism; do not turn normal upstream branch inputs into arbitrary fixed URLs just to pin them.
- **Service and package activation:** never build/download packages at unit startup, enable all migrated user services automatically, or run blanket `make`, destructive cleanup, `git clean -fdx`, Nix garbage collection or deletion of recovery data to force a migration. Use immutable Nix store paths or defined profile references in systemd units and explicit activation/rollback. Do not alter a running XMonad/XRDP/SSH session, disk, secrets or Enpass integration without a safe test and recovery path.
- **Testing contract:** on every substantive change, use the applicable Nix evaluation/check, offline QEMU tests, and the checked-in integration/E2E scripts invoked by CI; run native Git hooks and privacy checks when a connected development runtime supports them. The archived dotfiles Makefile and test workflow are retired: the current repository's own `nix develop` shell supplies reproducible dependencies, while the scripts are the unified manual/CI test entrypoints. Never bypass or silently skip an applicable gate; if a GitHub connector writes source without running local hooks/tests, report that limitation and do not call the change locally tested. For live GCE/Dell/ARM changes, require separately reported operator/device E2E after offline CI gates.
- **Historical recovery:** do not merge archived dotfiles history or deprecated secret-bearing commits into this public repository. Extract reviewed, necessary **source content only**, with privacy checks, and no private OptMem data/worktrees or Enpass vault. Private recovery repositories and devices are independent: never copy their data to `klarkc/os` or mutate them as part of a code migration.
